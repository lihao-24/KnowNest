## 一、执行摘要

当前项目已经完成了一个可运行的 MVP 竖切，核心链路已基本打通：

- 已有真实 Supabase Auth 登录与受保护工作台。
- 已有桌面三栏工作台 UI。
- 已有考生画像规则抽取。
- 已有基于结构化数据的冲稳保候选初筛。
- 已有右侧总结区联动展示画像、缺失信息、候选、来源与待核验事项。
- 已有数据库 schema、迁移、样例数据导入脚本和一批单元测试。

但从设计文档定义的目标来看，当前仍处于“开发态 MVP 骨架 + 推荐闭环初版”阶段，还不是可完整交付的第一版。最关键的未完成项包括：

- 真实 LLM Provider 尚未接入。
- 志愿篮保存能力尚未实现。
- 多会话能力未完整闭环。
- `score_segments`、`school_documents`、RAG 链路未完成。
- 浏览器级 smoke / e2e 验证未建立。

综合判断：

> 当前项目已具备 MVP 核心闭环雏形，整体完成度约 60% ~ 70%。

## 二、审查范围与判定基准

### 2.1 产品目标基准

依据 `docs/specs/initial-product-scope.md` 与 `docs/specs/mvp-product-design.md`，MVP 的核心目标是：

1. 面向河南省高考志愿辅助。
2. 通过对话采集考生画像。
3. 在信息不完整时优先追问，不直接生成完整结论。
4. 基于结构化数据给出冲、稳、保候选。
5. 在右侧持续沉淀画像、来源、风险和待核验事项。
6. 支持候选保存到志愿篮。

### 2.2 实施阶段基准

依据 `docs/plans/2026-06-09-mvp-implementation-plan.md`，重点检查以下阶段的实际落地情况：

- 阶段 1：统一登录
- 阶段 2：业务数据库与 schema
- 阶段 3：数据导入
- 阶段 4：画像提取
- 阶段 5：推荐规则服务
- 阶段 6：LLM 问答编排
- 阶段 7：工作台 UI
- 阶段 8：Docker 本地部署

## 三、当前已完成能力

### 3.1 登录与受保护工作台

已实现真实 Supabase Auth 登录链路与受保护工作台访问：

- 登录页：`src/app/login/page.tsx`
- 登录页壳：`src/components/LoginPageShell.tsx`
- 工作台页：`src/app/workspace/page.tsx`
- 服务端鉴权：`src/lib/auth/server.ts`
- 登录路由：`src/app/auth/sign-in/route.ts`
- 退出路由：`src/app/auth/logout/route.ts`

审查结论：

- 已基本满足实施计划中“统一登录”的核心目标。
- 服务端获取用户身份而非依赖客户端传 `user_id`，边界清晰。

当前前端已实现与产品设计基本一致的三栏布局：

- 左侧会话列表
- 中间聊天问答区

核心实现：

右侧总结区已具备以下板块：

- 考生画像

- 信息架构层面已明显对齐 `docs/specs/mvp-product-design.md`。

## 四、部分完成能力

### 4.1 阶段 2：业务数据库能力

虽已具备 schema 和 repository，但仍未完全闭环：

- 真实 Postgres 端到端验证不充分。
- 用户隔离更多停留在 repository 层约束，缺少端到端验证证明。
- 工作台页面初始化时未完整恢复数据库中的历史状态。

审查结论：

- 阶段 2 属于“基础完成，使用体验未闭环”。

### 4.2 阶段 4：画像管理

当前已实现规则提取，但未实现：

- 用户手动修正画像
- 软字段确认流程
- 前端可编辑/确认画像交互

审查结论：

- 画像“提取”完成度较高。
- 画像“纠错与确认”尚未完成。

### 4.3 阶段 5：推荐规则服务

已有初筛能力，但以下能力尚不完整：

- 未接入更完整的分段统计辅助判断

- 阈值模型仍较粗

审查结论：

当前工作台已有主形态，但以下体验仍缺：

- 新建会话真实行为

## 五、尚未完成的关键项

### 5.1 真实 LLM Provider 接入

当前 `src/lib/ai/provider.ts` 虽检测 provider 配置，但即使配置存在，仍返回 demo 文本。

这意味着：

- 真实大模型问答并未接入
- system prompt 与结构化上下文尚未驱动真实模型输出
- 当前“AI 回答”实质仍是模板化 demo

审查结论：

- 这是当前最关键、最影响 MVP 真实性的缺口。

### 5.2 志愿篮保存能力

数据库 schema 中已有 `saved_choices`，但尚未发现以下实现：

- repository
- API
- 前端保存动作
- 候选收藏/备注交互

审查结论：

- 这属于设计文档中明确承诺、但当前尚未落地的核心功能。

### 5.3 完整多会话能力

当前左侧会话列表已存在，但还缺：

- 新建会话真正创建新 session
- 切换会话恢复对应消息与画像
- 以当前选中的 session 为上下文继续问答

审查结论：

- 当前更像“单会话 + 会话列表展示”，而不是完整的多会话工作台。

### 5.4 `score_segments` / `school_documents` / RAG

设计与架构文档提及的重要数据链路尚未完成：

- `score_segments`
- `school_documents`
- 文档检索 / RAG
- 与章程、方法论资料的结构化关联

审查结论：

- 当前系统能做“基于历史招生记录的初筛”。
- 还不能做“基于更完整证据体系的可信解释”。

### 5.5 浏览器级 smoke / e2e

当前 `package.json` 中无 `e2e` 脚本，也未见 Playwright 等浏览器测试设施。

审查结论：

- 缺少用户主路径验证，尤其会影响登录、聊天、右栏联动、多会话等关键体验的稳定性判断。

## 六、文档与实现不一致项

### 6.1 `enrollment_plans` 进度描述滞后

实施计划部分位置仍将 `enrollment_plans` 导入描述为待完成，但代码中已经存在：

- 导入脚本
- 数据库导入 helper
- 相关测试

审查结论：

- 文档滞后于代码，应更新计划文档中的状态描述，避免误判进度。

### 6.2 完整推荐触发条件与当前实现存在偏差

设计文档将“是否考虑国家专项计划”列为完整推荐前的关键条件之一。

但当前 `RequiredProfileField` 仅包括：

- `score`
- `rank`
- `subjectType`
- `primaryGoal`

未把 `eligibleNationalSpecialPlan` 作为硬阻断条件。

审查结论：

- 当前实现可能在国家专项资格未明确时，过早进入推荐阶段。
- 这会影响产品边界一致性。

### 6.3 工作台初始化状态与真实持久化状态不一致

当前 `src/app/workspace/page.tsx` 初始化 summary 时使用的是空画像生成逻辑，而不是从用户最近会话或最近画像恢复。

审查结论：

- 数据层虽然已有持久化，但首屏体验未与之对齐。
- 这会削弱“会话可持续”的产品感受。

## 七、代码质量与实现风险

### 7.1 代码结构优点

当前代码结构整体清晰，领域分层合理：

- `auth`
- `db`
- `profile`
- `admissions`
- `recommendation`
- `chat`
- `ai`

优点包括：

- 模块职责较明确
- 类型边界较清楚
- 便于继续演进
- 单测切入点明确

### 7.2 主要实现风险

#### 风险 1：数据库失败时回退过于静默

`src/lib/db/chat-repository.ts` 中在数据库不可用或查询失败时，会直接回退 demo 数据或跳过持久化。

风险在于：

- 容易掩盖真实数据库故障
- 用户可能误以为当前数据为真实持久化数据
- 开发排障时定位成本提高

#### 风险 2：推荐结果可信度仍偏低

当前推荐引擎仍主要依赖：

- 历史招生记录
- 粗粒度位次比例
- 少量风险标签

缺少：

- 更丰富的证据维度
- 更严格的章程约束
- 更成熟的风险分层

#### 风险 3：多会话语义未闭环

当前持久化已存在，但前端会话切换、首屏恢复、上下文续聊还未闭环，容易导致：

- session 概念与实际使用行为不一致
- 用户难以理解“当前咨询”与“最近会话”的真实关系

#### 风险 4：AI 层与产品承诺不匹配

当前 UI 呈现已经很接近“智能志愿工作台”，但 AI 层仍是 demo 文本，会导致：

- 功能观感先于能力实现
- 如果过早对外试用，用户预期可能明显高于当前真实能力

## 八、建议优先级

### P0：必须优先完成

1. 接入真实 LLM Provider
   - 完成真实模型调用
   - 建立 system prompt
   - 将结构化候选、来源、边界信息传给模型

2. 补齐多会话闭环
   - 新建会话
   - 切换会话
   - 恢复消息历史与画像
   - 以当前会话继续问答

3. 统一“完整推荐触发条件”
   - 明确国家专项资格是否为阻断条件
   - 让实现与产品文档保持一致

### P1：尽快补齐

4. 实现志愿篮保存能力
   - 保存候选
   - 保存备注、风险、来源摘要
   - 衔接后续导出能力

5. 修正工作台首屏 hydrate 行为
   - 用最近 session / profile 初始化页面
   - 让持久化成果真正体现在用户体验中

6. 建立浏览器级 smoke / e2e 验证
   - 登录
   - 进入工作台
   - 发起问答
   - 右栏联动
   - 会话切换

### P2：增强可信度与完整度

7. 接入 `score_segments`
8. 接入 `school_documents` 与 RAG
9. 细化风险标签与推荐阈值
10. 补窄屏抽屉交互与设计稿细节对齐
11. 增强部署验证与 Docker 文档

## 九、阶段性结论

从“是否已经有东西能跑”来看，答案是肯定的。

从“是否已经达到设计文档所描述的第一版可用产品”来看，答案是否定的。

当前项目最准确的判断是：

> 已完成一个质量不错的 MVP 技术骨架和核心推荐闭环初版，具备继续快速迭代的良好基础；但离设计文档意义上的完整一版，还差 AI、会话、收藏、证据链和验证体系这几块关键拼图。

## 十、建议后续动作

建议在下一轮开发中，优先围绕以下顺序推进：

1. 真实 LLM 接入
2. 多会话闭环
3. 志愿篮保存
4. 浏览器级验证
5. 证据链扩展（score_segments / school_documents / RAG）

完成上述 1~4 项后，再进行一轮以“真实账号 + 真实数据库 + 浏览器路径”为核心的阶段性复审。
