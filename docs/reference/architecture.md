# 架构参考

## 当前目标

本项目第一阶段只服务河南省出分后的正式志愿辅助筛选，范围限定为近三年本科批和国家专项计划。产品形态是本地运行的类 ChatGPT Web 端，后续通过个人域名暴露访问。

系统目标不是“让大模型凭感觉报志愿”，而是把河南结构化招生数据、官方资料和张雪峰式咨询方法结合起来，辅助用户理解选择、筛候选、识别风险。

## 总体架构

```text
用户提问
  ↓
对话编排层
  ↓
考生画像提取与缺口判断
  ↓
结构化数据查询与规则筛选
  ↓
文档 RAG 检索
  ↓
LLM 生成解释和追问
  ↓
聊天区 + 右侧总结区展示
```

## 双层 RAG

### 数据 RAG / 结构化查询层

负责处理可以被结构化的数据：

- 河南近三年本科批投档/录取数据
- 河南近三年国家专项计划投档/录取数据
- 一分一段表
- 批次线、特殊类型线
- 招生计划
- 学校、专业、专业组或志愿单位信息
- 选科或科类限制
- 招生章程中的硬性限制

这一层优先使用数据库查询和规则过滤，不依赖向量相似度猜答案。涉及分数、位次、批次、计划数、录取风险时，必须先经过这一层。

### 方法论 RAG / 文档检索层

负责检索解释性和风格性资料：

- 河南志愿填报政策说明
- 高校招生章程文本
- 专业介绍和就业质量报告
- `xuefeng-agent` 精选方法论参考
- 项目自有咨询流程和风险提示模板

这一层用于回答“为什么这么建议”“这个专业风险在哪”“普通家庭该怎么取舍”等问题。它不能单独决定候选学校和录取概率。

## 规则筛选优先

LLM 不能直接决定“能上哪些学校”。推荐流程必须先经过规则筛选：

1. 校验河南省、年份、批次和计划类型。
2. 校验考生分数、位次、科类或选科。
3. 校验国家专项资格等硬条件。
4. 根据近三年最低位次和计划变化筛候选。
5. 按冲、稳、保做初步分层。
6. 再交给 LLM 解释取舍和风险。

LLM 可以调整表达、提醒风险、提出补充问题，但不能绕过规则层给出未引用数据的具体录取结论。

## 核心模块

### 当前代码映射

截至 2026-06-11，当前实现已落到以下目录：

- `src/app/`：Next.js App Router 页面和 API routes。
  - `/login`：工具入口式登录页。
  - `/workspace`：受保护三栏工作台。
  - `/api/auth/me`：返回服务端认证得到的当前用户。
  - `/api/chat`：接收用户消息并调用服务端对话编排，支持按 `sessionId` 续聊。
  - `/api/chat/sessions`：创建当前用户的新聊天会话。
  - `/api/chat/sessions/[sessionId]`：按当前用户读取指定会话消息历史和画像 summary。
  - `/api/chat/sessions/[sessionId]/profile`：按当前用户和会话保存手动修正画像。
  - `/api/saved-choices`：按当前用户保存和读取志愿篮候选。
  - `/api/saved-choices/[candidateId]`：按当前用户取消保存候选。
- `src/components/`：登录页、工作台、状态标签等 UI 组件。
- `src/lib/auth/`：Supabase server auth helper、真实登录/退出和本地兜底 demo auth。
- `src/lib/db/`：Postgres 连接、迁移、聊天会话 repository、消息历史、candidate profile 和 saved_choices 持久化。
- `src/lib/profile/`：考生画像提取和缺失字段判断。
- `src/lib/admissions/`：`admission_records`、`enrollment_plans`、`score_segments`、`school_documents` CSV 解析、校验、样例/数据库查询和导入 helper。
- `src/lib/recommendation/`：第一版内存数据推荐规则。
- `src/lib/chat/`：服务端对话编排、summary 生成和前端数据结构。
- `src/lib/ai/`：OpenAI-compatible Provider 边界，配置齐全时调用 Chat Completions；输入使用服务端结构化 summary，并有候选越权安全回退。
- `src/lib/rag/`：`school_documents` 关键词检索样例链路，不使用 embedding/pgvector。
- `scripts/`：数据库迁移和招生数据导入/smoke 脚本。

当前可运行体验是 Supabase Auth + 样例数据竖切；`DATABASE_URL=disabled` 时读取 `fixtures/admissions/` 下的虚构样例 CSV，配置数据库时优先查询 `admission_records`、`enrollment_plans`、`score_segments` 和 `school_documents`。本地 Postgres 已可通过 `POSTGRES_PORT=55432` 启动，迁移和样例 CSV 导入已有脚本；默认 browser smoke 已覆盖 demo auth 下的工作台、问答、右栏联动、画像修正、志愿篮保存/取消保存和多会话切换。真实账号浏览器端到端 smoke、真实 Postgres 浏览器端到端 smoke、真实河南招生数据和完整章程风险分析尚未完成。真实 LLM Provider 已有服务端接入边界，但尚未用真实 key 做浏览器 smoke。

### 前端层

建议形态：

- 左侧：聊天会话列表。
- 中间：主问答区。
- 右侧：已总结内容区，包括考生画像、候选清单、数据来源、风险提示和待核验事项。

第一阶段 UI 不急于定稿，后续可用 Pencil 先设计一版。

### 对话编排层

负责：

- 管理多轮会话。
- 提取用户输入中的考生画像。
- 判断缺失信息并生成追问。
- 调用数据查询、规则筛选、文档检索和 LLM。
- 把回答、来源、候选项和风险结构化返回前端。

### 考生画像层

第一阶段字段：

- 省份：固定河南。
- 分数。
- 位次。
- 科类或选科。
- 本科线、特殊类型线。
- 是否具备国家专项计划资格。
- 专业兴趣。
- 明确排斥项。
- 地域偏好。
- 家庭资源和预算。
- 核心诉求：就业、考公、考研、稳定、高薪、离家近等。

画像可以从对话中逐步提取，但必须允许用户手动修正。

### 数据层

第一阶段只接入：

- 河南近三年本科批。
- 河南近三年国家专项计划。
- 河南近三年一分一段表。
- 与候选项相关的高校招生章程和招生计划。

数据必须保留来源、年份、批次、计划类型和可信等级。详见 `data-trust-model.md`。

### 规则层

负责：

- 批次和计划类型过滤。
- 国家专项资格过滤。
- 科类/选科要求过滤。
- 位次区间筛选。
- 近三年波动分析。
- 招生计划变化提示。
- 冲稳保初分层。
- 特殊限制提示，例如体检、单科、外语语种、学费、中外合作等。

规则层输出候选事实，不负责生成最终自然语言。

### LLM 层

负责：

- 追问缺失信息。
- 解释候选项。
- 对比学校、专业和城市。
- 用张雪峰式但不过度冒犯的风格提示风险。
- 生成用户可读的核验清单。

LLM 输入应包含规则层筛出的候选、检索到的资料和明确的数据声明。LLM 输出必须标注哪些是官方数据、哪些是经验判断。

## 本地部署方向

推荐：

- Next.js + React + TypeScript。
- Docker 本地运行。
- 服务端调用 OpenAI-compatible Provider。
- 复用统一 Supabase Auth 做登录。
- 本项目使用独立业务数据库，推荐 Postgres，并预留后续 `pgvector`。
- Docker Compose 本地运行，后续通过个人域名和反向代理暴露访问。

前端不得直接访问模型 Provider 或持有模型密钥。

认证和存储边界详见 `auth-and-storage.md`。

## 关键边界

- 不做全国通用系统。
- 不覆盖专科、提前批、强基、艺术体育等复杂批次，除非后续单独扩展。
- 不把 `xuefeng-agent` 原知识库当作可信录取数据源。
- 不用百度搜索结果直接生成录取判断。
- 不承诺录取结果。
- 不生成无法追溯来源的具体分数线、位次和计划数。
